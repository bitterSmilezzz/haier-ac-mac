### P2 — 建议

- **`Sources/HaierACCore/Models.swift:80-97`（`ACModeCode.match` 的兜底分支），影响 `AppModel.swift:592` 与 `StatusItemController.swift:101`** — 无法识别的模式串被兜底成「制冷」，滤网磨损系数从旧实现的中性 1.00 变成 1.20–1.35。
  - 为什么是问题：重构前的 `calculateFilterWearFactor` 是 `if m == "0" || 制冷 … else { modeFactor = 1.00 }`，**未识别的模式一律走中性 1.00**。重构后统一走 `ACModeCode.match(from:)`，而该函数第 96 行 `return .cooling` 是最终兜底——于是任何落在 `{0,1,2,3,4,6}` 之外、且不含「冷/热/暖/风/湿/自」的取值（例如云侧将来新增的 `"5"`、`"7"`，或「智能」「节能」这类中文描述）都会被当成**制冷**，按 1.20（或室内温 > 设定温时 1.35）计等效工时，比中性值高 20%–35%。触发面很窄（`AppModel.swift:863` 的取值是 `attrs["operationMode"]?.stringValue ?? "0"`，正常路径给的是已知码），但方向是**高估磨损**，会让用户提前收到「滤网该洗了」的提示。
    同一兜底还影响 `StatusItemController.swift:101` 的 tooltip：模式属性缺失或无法识别时，会向用户显示「❄️ 制冷」，而实际工况未知——这是**把未知说成已知**。
  - 建议：给「无法识别」一个显式语义，而不是借用 `.cooling`。最小改法是让 `match` 返回可选值（`static func match(from raw: String?) -> ACModeCode?`），调用点各自决定兜底：`calculateFilterWearFactor` 用 1.00（保持旧行为）、`StatusItemController` 显示「—」或直接省略模式字段、`EnergyAnalyticsEngine` 保留现有的 `.cooling` 兜底（那里旧代码本来就是 `?? "0"`，行为等价）。若不改签名，至少把第 96 行的兜底改成 `.auto`（`modeFactor = 1.00`、tooltip 显示「自动」），语义比「制冷」更接近「未知」。
  - **不确定**：本轮无法确证线上设备是否真会返回 `{0,1,2,3,4,6}` 之外的值——若协议保证只有这几个码，本条仅为健壮性建议。**验证方式**：看设备详情里 `operationMode.valueRange.dataList` 的 `data` 全集，或在 `AppModel.swift:863` 附近临时打一行日志收集实际取值分布。
