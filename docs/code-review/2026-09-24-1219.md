### P1 — 重要

- **`Sources/HaierACApp/Voice/VoiceCapsuleWindowController.swift:302`（可达性门禁的位置）** — 门禁加在**设备分发之前**，于是把**纯本地**的语音指令一并锁死：`.stopSleepCurve`（`:466`）、`.cancelSchedules`（`:443`）、`.queryStatus`（`:359`）、`.querySleepReport`（`:474`）在目标设备离线或网关重连时**一律被拒**，报「「XX」当前离线，无法执行语音指令」。
  - 为什么是问题：这四条指令**不向设备发送任何东西**，已逐条核实——
    - `stopSleepCurve()`（`AppModel.swift:1388-1403`）只做 `archiveSleepSession` → 清 `activeSleepSession` → 停本地环境音 → `wakeScheduler()` → `writeWidgetSnapshot()`；
    - `.cancelSchedules` 分支只改 `model.scheduledActions`，其 `didSet`（`AppModel.swift:975-979`）仅写 `UserDefaults`；
    - `.queryStatus` 与 `currentIndoorTemperature(for:)`（`AppModel.swift:1303-1305`）读的是本地 `attributes` 缓存。
    而**这正是 v1.9.28 在 UI 层刚修好的同一类缺陷**：`3669f1b` 的提交说明与 README 都写着「由于 `stopSleepCurve()` 仅执行纯本地状态归档、定时器清理与助眠音频停止，**解除了**对其『停止』按钮的不可达禁用，确保设备离线或网关断开时用户依然能随时终止睡眠会话」。本轮语音层把同一个门禁原样加回了执行入口——README 里那句判据现在只对菜单/按钮成立，对语音不成立。
  - 影响：设备在睡眠中途掉线 → 用户对着语音说「停止睡眠」被拒，反而只能去主窗口点按钮；设备离线时问「客厅现在多少度」也被拒，尽管缓存里有值（`.queryStatus` 的 `else` 分支本来就是读缓存的）。
  - 建议：把门禁下移到**真正会下发指令**的分支里（`.setPower` / `.setTemperature` / `.adjustTemperature` / `.setMode` / `.setWindSpeed` / `.startSelfCleaning` / `.schedulePower` / `.scheduleCountdown` / `.startSleepCurve` / `.applyScene`），对 `.stopSleepCurve` / `.cancelSchedules` / `.queryStatus` / `.querySleepReport` 放行——与 UI 层 `MenuBarControlsView` 的门禁粒度保持一致。`case .applyScene` 保持门禁是对的（它会下发，且 `AppModel.applyScene:2210` 已有逐设备守卫）。
  - 验证方式：把目标设备置为离线，对着语音胶囊说「停止睡眠」与「现在多少度」——当前均返回离线错误。

- **`Sources/HaierACApp/Voice/VoiceCapsuleWindowController.swift:211` 与 `Sources/HaierACApp/AppIntents.swift:267`（`TurnOnAllACIntent`，`:258` / 注册于 `:334` 与 `:423`）** — 「全屋开机」被实现为 **`applyPresetToAllDevices(mode: .cooling, temperature: 26.0)`**，即强制切制冷 26°C；而解析器把同一句话解析成**不带任何模式与温度**的 `.turnOnAll`。
  - 为什么是问题：两侧对 `.turnOnAll` 的语义定义不一致。解析器侧的用例明确断言 `VoiceCommandParser.parse("全屋开机")` == `.turnOnAll`（`VoiceCommandParserTests.swift` 新增的 `on3`），即「开机」就是开机；执行侧却额外注入了制冷 26°C。测试只断言枚举、断言不到这层注入，所以这个分歧在测试里是**看不见**的。
    而 v1.9.33 的标题与 README 首条都宣称「**彻底消除**「全屋开暖气/制热」被 `isAllPowerOn` 误判为开机并执行默认制冷 26°C 导致的**冷暖颠倒严重缺陷**」。实际修的是「带模式词的表述被误路由」，**裸开机表述仍在执行默认制冷**：冬季说「全屋开机」「打开所有空调」，或对 Siri 说「开启所有空调」「全屋开机」（本轮新注册的 `TurnOnAllACIntent`，`description` 自己写着"并设置为清爽制冷 26°C"），全屋空调会被切成制冷。
  - 建议：二选一。① `.turnOnAll` 改成只下发 `onOffStatus = true`（`sendAttributeToDevices("onOffStatus", value: .bool(true), deviceIds:)` 这条路径在 `executeMultiDeviceCommand` 里已有，可直接复用），模式与温度留给 `presetAll`；② 保留「开机即制冷 26°C」的产品语义，但把 README 首条的「彻底消除冷暖颠倒」改成有边界的措辞（例如「消除带模式词的表述被误判」），并把 Siri 意图的 `title`/`description` 与语音提示改为「全屋制冷 26°C」而不是「开启全屋空调」——让用户在下指令前就知道会发生什么。
  - 说明：`.turnOnAll → 制冷 26°C` 这一映射本身由 v1.9.30 引入（`TurnOffAllACIntent` 同批），**在本轮窗口之内**，故按新问题记录。

### P2 — 建议

- **`Sources/HaierACApp/Voice/VoiceCapsuleWindowController.swift:443-451`（`case .cancelSchedules` 的兜底分支）** — 目标设备没有定时任务时，兜底会**清空全部设备**的定时任务。
  - 为什么是问题：新逻辑是「先按 `deviceId` 过滤，有就只删本设备的；本设备没有、而别的设备有，就 `model.scheduledActions.removeAll()` 并提示『已取消所有定时任务』」。于是同一个「取消定时」口令会随目标设备的状态在**设备级**与**全屋级**两种语义之间跳变：客厅有定时 → 只删客厅；再喊一次（客厅已空）→ **顺手删掉主卧的定时**，而用户从未说过「全部」。
    这与本项目 v1.9.32 自己立的原则直接冲突——README 该条写的是「严格绑定当前用户选中的 `deviceIds` 集合，**彻底杜绝部分勾选时穿透控制未选中房间空调的越权缺陷**」。本轮在语音链上又放了一个穿透口。
  - 建议：删掉 `else if model.scheduledActions.count > 0` 这条兜底，本设备没有就回「当前没有正在运行的定时任务」；确实需要全屋取消时，走显式的「取消所有定时」口令（可新增一个 `cancelAllSchedules` 指令），不要在同一个口令里做隐式升级。

- **`Sources/HaierACApp/AppModel.swift:2709` / `:2735` 与 `Sources/HaierACApp/Views/BatchControlView.swift:72`** — 「是否全屋」用**计数相等**判定，而不是集合相等：`let isAll = (deviceIds == nil) || (targets.count == allUnifiedDevices.count)`、`let isAllSelected = deviceIds.count == model.allUnifiedDevices.count`。
  - 为什么是问题：`deviceIds` 来自 `DeviceListView.selectedDeviceIds`（`Set<String>`）。若用户选中的设备被解绑/移除，集合里会留下**已不存在的 id**，此时 `count` 仍可能与 `allUnifiedDevices.count` 相等而两个集合并不相同 → 按钮显示「全屋关机」、`operationNotice` 显示「已关闭全屋 N 台」，实际目标却是另一批设备。这与上一轮刚闭环的 P2-2（`turnOffAllItem` 标题计数与实际目标集不同源）是同一类口径问题，只是换成了「计数 vs 集合」。
  - 建议：判据改成集合包含关系，例如 `let isAll = deviceIds == nil || Set(targets).isSuperset(of: allUnifiedDevices.map(\.id))`；视图侧同理用 `Set(deviceIds) == Set(model.allUnifiedDevices.map(\.id))`。若无法判断就退化为中性文案（「关机」不带「全屋/所选」前缀），避免文案与目标不一致。

- **`Sources/HaierACCore/VoiceCommandParser.swift:366` 与 `:473` / `:486`（新增的口语兜底与结构判定）** — 新增的宽松兜底**不识别否定**，容易把「别关」判成「关机」。
  - 为什么是问题：`:366` 的兜底是「含『所有/全部/全屋/全都』**且**含『关』或『停』」即返回全屋关机。于是「全屋空调别关了」「所有空调先不要关」这类口语会命中全屋关机。`:473` 的 `text.hasSuffix("关了")` / `hasPrefix("关")` 同理会命中「不要关了」。解析器全仓本来就没有否定处理（历史 `offKeywords` 里的「别吹了」是个例外式的固定短语），但本轮把兜底放宽后，命中的**入口数量级增加**，风险随之放大。
  - 建议：在 `parse` 顶层加一条前置过滤——命中「别/不要/不用/先不/取消关」等否定前缀时，先把否定词与紧随的动作用对消掉再判定；或至少在 `isAllPowerOff` / `isPowerOff` / `isPowerOn` 入口处 `guard !containsAny(["别关","不要关","不用关","先别","别开"])`，让「不要做某事」不落到「做某事」上。

`scan_projects.py` 的 docstring 要求 `state.json` 的 `last_review` 写「已覆盖文件中最老的 mtime」，本任务书第 4 步要求写「本轮扫描时间」。有截断时两者不兼容：写扫描时间会让被 `--max-files` 砍掉的**已提交**文件永久失联。本轮 haier 恰好是「截断 7 + 已提交」的组合，且**未补跑扩大上限的扫描**，因此这 7 个文件若在下一轮的 `last_review` 之后未被再次改动，就会永久落在增量窗口之外。建议固化方案（二选一）：

1. 任务书改为写「已覆盖文件中最老的 mtime」——语义上更严谨，代价是本轮已覆盖文件在下一轮会被重复列出一次；
2. 保留写扫描时间，但扫描器在有 `truncated > 0` 时输出一个显式的 `next_last_review` 字段（取被截断文件的最老 mtime），由任务写入 `state.json` 的另一个键，供下轮作为增量起点。

本轮按任务书写扫描时间（第 6 次触发）。
