### P1 — 重要

- **`Sources/HaierACApp/Audio/AmbientSoundEngine.swift:112-152`（`stop()`）** — 被取消的淡出任务仍会执行收尾，把刚重启的引擎停掉。
  - 为什么是问题：淡出 Task 的循环体是 `for … { try? await Task.sleep(…); if Task.isCancelled { break }; … }`，`break` 之后**无条件**执行 `self.activeGain = 0.0`、`self.engine?.stop()`、`self.isPlaying = false`。而 `play()` 在「引擎已在运行」这条路径上只做 `fadeTimer?.cancel()` + 新建淡入任务，并不检查旧任务是否还会收尾。于是操作序列「停止 → 1.5 秒淡出窗口内再点播放」的结果是：淡入任务刚把引擎拉起来，被取消的淡出任务随后醒来把引擎 `stop()` 掉、`isPlaying` 置回 `false`——界面显示在播、实际无声。菜单栏白噪音快捷开关走的是 `if isPlaying { stop() } else { play() }`，连点两次即命中；`toggle()` 同理。同理，淡出窗口内 `isPlaying` 仍为 `true`，第二次点击走的是 `stop()` 分支（`guard isPlaying` 通过），所以「停止后立刻重启」在 1.5 秒内根本没有可用的路径。
  - 建议：给淡入/淡出任务加代次（generation）标记，收尾前比对 `guard !Task.isCancelled, generation == self.fadeGeneration else { return }`；退一步的写法是把收尾整段放进取消判断之内。另建议 `stop()` 在进入淡出时就置 `isPlaying = false`（UI 语义与按钮行为一致），淡出只影响 `activeGain`。

- **`Sources/HaierACApp/StatusItemController.swift:38-48`** — 菜单栏刷新链丢掉了 `menuBarDeviceId` 与 `menuBarShowTemperature`，设置改动不再即时反映。
  - 为什么是问题：原实现是 `model.$attributes.combineLatest(model.$menuBarDeviceId, model.$menuBarShowTemperature, model.$devices)`；本次改为 `Publishers.Merge4($attributes, $devices, $isSelfCleaningActive, $activeSleepSession)`，前两个触发源消失了。而 `refreshTemperature()` 读的 `model.menuBarTemperatureText`（`AppModel.swift:413-418`）恰恰由 `menuBarShowTemperature` 与 `menuBarDeviceId` 决定：在设置里关掉「菜单栏显示温度」、或把菜单栏绑定切到另一台设备后，菜单栏标题不会立刻更新，要等下一次 `attributes` 推送才纠正。这是本次改动引入的行为回归（不是新功能缺失）。
  - 建议：把两个 publisher 加回合并链（`Publishers.MergeMany`，或 `CombineLatest4(attributes, devices, menuBarDeviceId, menuBarShowTemperature)` 再与 `isSelfCleaningActive` / `activeSleepSession` 合并）。

### P2 — 建议

- **`Sources/HaierACApp/StatusItemController.swift:218-228`（`openFilterCare`）** — 菜单项文案与动作不符。
  - 为什么是问题：菜单项标题是「滤网保养与自清洁 (洁净度 X%)...」，点击却只调 `openMainWindow()`，不打开滤网面板。用户以为直达、实际到了主窗口，还得自己找入口。
  - 建议：或改成能真正打开 `FilterCareSheet` 的路由（需要主窗口侧配合一个「打开指定 sheet」的入参），或把标题改为「打开主窗口查看滤网与自清洁」——文案与动作对齐即可。

- **`Sources/HaierACApp/AppModel.swift:470-478`（`filterAccumulatedMinutes(for:)` / `lastFilterCleanedDate(for:)`）** — 未登记设备会继承主设备的旧累计值。
  - 为什么是问题：`deviceFilterMinutes[deviceId]` 缺失时回退到全局遗留字段 `filterAccumulatedMinutes`。该字段在旧版只统计「第一台设备」，因此升级后新加入的第二、第三台设备在首次采样落库前，会显示主设备的累计运行时长与清洁度——同一份数字被三台设备共用。一旦 `accumulateMinuteTick` 跑过一轮就会自建条目并纠正，所以影响窗口约 1 分钟；但升级瞬间、以及刚添加设备的瞬间都会显示错误值。
  - 建议：回退只对「旧版遗留的那一台设备」生效（例如仅在 `devices.first?.id == deviceId` 时回退），其余设备缺失即返回 0。

- **`Sources/HaierACApp/AppModel.swift`（`startSelfCleaning(deviceId:)`）** — 公开 API 不防重复启动，也不撤销上一台设备的自清洁指令。
  - 为什么是问题：方法内部直接覆盖 `selfCleaningDeviceId` 并 `selfCleaningTask?.cancel()`，但没有对**上一台设备**下发 `…Status = false`。当前 UI 用 `.disabled(model.isSelfCleaningActive)` 挡住了「清洁中再启动另一台」，所以暂时不可达；但这是靠调用方兜底，公开方法自身的契约不完整，将来从别的入口（快捷指令 / 侧车脚本）调用就会让旧设备停在自清洁态而界面只认新设备。
  - 建议：在覆盖前先 `if isSelfCleaningActive { stopSelfCleaning() }`，或把 `guard !isSelfCleaningActive else { … }` 的拒绝逻辑写进方法内并在调用处去掉 `.disabled`。

- **`Sources/HaierACApp/Views/MenuBarControlsView.swift`（`ambientSoundPod`）** — 直接读 `AmbientSoundEngine.shared.isPlaying` 但未观察该对象。
  - 为什么是问题：本视图只声明了 `@EnvironmentObject var model: AppModel`，`AmbientSoundEngine.shared` 是另一个 `ObservableObject`，未被 `@ObservedObject` / `@StateObject` 订阅。因此从**主窗口**播放或暂停白噪音时，pod 的图标（`waveform` / `speaker.slash`）与文案不会重渲染，要等 `model` 的某个 `@Published` 变化顺带刷新。`selfCleaningPod` 不受影响（读的是 `model` 的 `@Published`）。
  - 建议：`@ObservedObject private var ambient = AmbientSoundEngine.shared`（或 `@StateObject` 不适用单例，用 `@ObservedObject`）。

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:241-266`（`accumulateSample`）** — 分钟口径（墙钟分钟）与 kWh 口径（设备总和）混在同一个记录里，容易误读。
  - 为什么是问题：`totalKWh` 逐设备累加，而 `totalMinutes` / `coolingMinutes` 等只按「该模式是否有设备在跑」+1 次。两台设备同时制冷 60 分钟时，记录是「60 分钟 / 2 倍电量」。这个口径本身站得住（分钟是墙钟时间），但字段名与 UI 都没写明，看报表的人很容易读成「设备分钟」。
  - 建议：至少在 `EnergyDayRecord` 的字段注释里写明「分钟为墙钟口径，多设备同时运行不重复计」，或在 UI 上加一句说明。

- **`.agents/sidecars/haier-ac-hourly-optimizer/executor.sh:52-56`** — 调度失败时的日志分支不可达。
  - 为什么是问题：`if [ -x "${AGENTAPI_BIN}" ]` 为真后执行 `"${AGENTAPI_BIN}" new-conversation … || { echo "[ERROR] agentapi call failed…"; }`，随后无条件 `echo "[COMPLETED] Scheduled task dispatch finished."`。脚本靠日志判断这轮到底有没有派发成功，而「COMPLETED」在失败时同样会打印，看日志只能靠肉眼分辨有没有夹着 ERROR 行。另外 `set -euo pipefail` 下 `cmd || { … }` 的复合结构本身没问题，但缺少可检索的退出标记。
  - 建议：失败分支里 `exit 1`（或至少把末尾那行改为带状态的分支输出），让日志有唯一可 grep 的成功标记。
