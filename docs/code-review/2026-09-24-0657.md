### P1 — 重要

- **`Sources/HaierACApp/Views/MenuBarControlsView.swift:97`（`sleepControlPod(device: device)`）** — 菜单栏的「智能睡眠」是命令入口，却没有纳入本轮的可达性门禁；提交声称的「彻底阻断不可达状态下的幽灵点击」在此处不成立
  - 为什么是问题：同一个 `VStack` 里，紧挨它的 `quickActionsPod`（:92-94）与 `temperatureBentoPod`（:109-112）、`modeAndFanPod`（:115-118）都加了 `.disabled(!reachability.isControllable)` + `.opacity(...)`，**唯独 `sleepControlPod` 两者都没有**（全文件 `grep isControllable` 只命中 3 处，不含它）。而它的空闲分支里有一个真实的命令按钮：`MenuBarControlsView.swift:829` 的「开启睡眠」→ `model.startSleepCurve(curve:deviceId:)`。`AppModel.startSleepCurve`（`AppModel.swift:1212` 起）**内部也没有任何可达性/在线守卫**——它直接归档旧会话、构造 `SleepSession`、按曲线下发温度。所以当网关重连中或设备离线时：横幅显示「控制指令暂不可用」、温度与模式控件变灰，**但"开启睡眠"仍可点，点了会真的开一个会话**，随后每次下发的指令都送不出去（或被静默丢弃），用户看到的是一段"什么都没发生"的睡眠记录。
  - 建议：给 `sleepControlPod(device: device)` 补上与邻居一致的 `.disabled(!reachability.isControllable)` + `.opacity(...)`；更稳妥的是**在 `AppModel.startSleepCurve` 入口也加一条守卫**（`guard reachability(for: deviceId).isControllable else { operationNotice = ...; return }`）——UI 门禁只能覆盖已加门禁的视图，本条的漏配正说明"靠每个视图记得加"不可靠，而 `startSleepCurve` 还有 4 个非 UI 调用方（`AppIntents.swift:208`、`VoiceCapsuleWindowController.swift:298`、`HaierACApp.swift:59`、`SleepCurveSection.swift:589`），它们同样绕过了门禁。
  - 顺带：`ambientSoundPod`（:105-107）是本地白噪音播放，不经设备，不加门禁是对的；`selfCleaningPod` 是纯状态显示，同理。

### P2 — 建议

- **`Sources/HaierACApp/AppModel.swift:339-347`（`reachability(for deviceId: String)`）** — 该重载**零调用点**（死代码），且未知设备回退 `.available` 是 fail-open；同时「设备是否可达」这一判据在本轮之后存在 **4 处独立实现**
  - 为什么是问题：全仓 `grep -rn "reachability(for:"` 只命中 4 处，其中 `AppModel.swift:341` 就在该重载自身内部（调 `DeviceInfo` 版），另外 3 处（`StatusItemController.swift:254`、`DeviceControlView.swift:36`、`MenuBarControlsView.swift:48`）传的都是 `DeviceInfo` —— **`String` 重载无任何外部调用者**。这与同一提交删除 `localizedName` 死代码、README 宣称「冗余死代码全面清理」直接冲突（同一提交里删一个、加一个）。更值得注意的是它内部的兜底：设备 ID 不在 `devices` 里时，只要 `gatewayConnected` 就返回 `.available` —— 对一个**完全未知的设备**报"可控制"，正是三态模型要堵的洞（虽然因无人调用暂无实际影响，但属于埋雷）。同型判据的其余 3 处实现：`MenuBarControlsView.swift:207-233`（header 用裸 `device.online` + `gatewayConnected` 自己拼 dot 颜色与文案）、`BatchControlView.swift:11-15`（自己算 `onlineCount`）、`AppModel.swift:2543-2547`（`sendAttributeToDevices` 自己过滤 `online`）。本轮新增的模型只在 3 个调用点被用上。
  - 建议：二选一——① 删掉 `String` 重载（无人用）；② 若打算给非 UI 调用方用，把未知设备的兜底改成 `.deviceOffline`（fail-closed）并说明理由。另建议把 `MenuBarControlsView` 的 dot/文案与 `BatchControlView` 的 `onlineCount` 都改为消费 `DeviceReachability`，让"可达性"只有一个定义——否则下一轮还会出现"某个视图忘了跟模型对齐"。

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:176-184`** — 未识别模式的"中性"估算在双温度有效时与 `.cooling` **逐位等价**，README 的「消除盲目强行兜底与功率虚标」在此情形下无实际变化；`indoor < target` 时则用制冷曲线给制热工况估值
  - 为什么是问题：新分支写的是 `380.0 + abs(indoor - target) * 95.0 + windOffset`，clamp `[180, 1200]`；`.cooling` 分支（:213-217 附近）写的是 `380.0 + max(0, indoor - target) * 95.0 + windOffset`，clamp `[180, 1450]`。**当 `indoor ≥ target` 时两式完全相等**（`abs` 与 `max(0,…)` 同值），只在 ΔT > 8.6 时因上限不同才分叉（1200 vs 1450）——而家用空调的室内外温差绝大多数落在 8.6 以内。也就是说：模式串无法识别 + 双温度有效时，估值仍是制冷曲线，只是封顶更低。反过来当 `indoor < target`（本该制热）时，"中性"给的是 `380 + ΔT*95`，而 `.heating` 是 `550 + ΔT*110`（:206-210 附近）——"中性"在制热方向上**系统性偏低**。所以这个分支既不中性、也没有真正"消除兜底"，只是把 `.cooling` 换了名字并加了个封顶。README 那句宣称与实现不符。
  - 建议：要么把注释与 README 改成如实的描述（「未识别模式按制冷功率曲线、以温差绝对值估算，上限 1200W」），要么换一条真正中性的基准（例如取制冷/制热两条曲线在 ΔT 处的均值，或直接给一个与模式无关的常数 + 风速偏移），并在注释里写明选了哪条、为什么。
  - 注：**上轮报的"双温度皆 nil 时与 `.cooling` 逐位等价"已闭环**（改为 `350 + windOffset`，clamp 180–600，见 :182-183），本条只针对双温度有效的情形。

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:43-76`（配合 `:143`）** — 自定义 Codable 只给 `unknownMinutes` 做了 `decodeIfPresent`，其余 7 个字段仍是必需解码，而历史是**整数组一次性解码**；README 的「100% 平滑反序列化」只覆盖了本次这一个字段
  - 为什么是问题：`init(from:)` 对 `totalMinutes` / `coolingMinutes` / `heatingMinutes` / `fanMinutes` / `dehumMinutes` / `totalKWh` / `totalCost` 用的都是 `try container.decode(...)`（缺字段即抛错），只有 `unknownMinutes` 是 `decodeIfPresent ?? 0`。加载侧是 `EnergyAnalyticsEngine.swift:143` 的 `try? JSONDecoder().decode([EnergyDayRecord].self, from: data)`——**数组里任何一条记录解码失败，`try?` 吞掉异常、整个 60 天历史静默清零**。本轮安全（`unknownMinutes` 已按可选处理，且 `fanMinutes` 等自 v1.9.20 该功能落地时就在，见 `git log -S fanMinutes`），但**这个提交本身就演示了"加字段"是常态**：下一个新增字段若照抄必需解码，就会重演"升级即清空历史"。而且清空是静默的（`try?` + 无日志），用户只会发现"用电记录没了"。
  - 建议：① 所有字段一律 `decodeIfPresent ?? 默认值`；② 加载改为逐元素容错（`decode([FailableRecord].self)` 或先取 `[JSONValue]` 再逐条 `try?`），保证一条坏记录不拖垮整个数组；③ 解码失败时至少 `AppLog` 记一条，别让数据丢失无声发生。
