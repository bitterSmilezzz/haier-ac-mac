### P2 — 建议

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:247-259`** — 未识别模式样本被排除出四个模式计数器，但**分母 `totalMinutes` 仍照常累加**，模式分布不再自洽
  - 为什么是问题：`if let sampleMode = ACModeCode.match(from: sample.modeCode) { ... }` 把未识别样本从 `runningCooling/Heating/Fan/Dehum` 全部排除——这一半是对的（消除「未识别记成制冷」的失真）。但 :271 的 `guard hasAnyRunningDevice, totalIncrementalKWh > 0.0` 只看有没有设备在跑，随后 :275 `historyRecords[idx].totalMinutes += incrementalMinutes` 无条件累加。于是当某台设备的模式长期不被识别（如上报 `"5"`）时：`totalMinutes` 在涨，而 `coolingMinutes + heatingMinutes + fanMinutes + dehumMinutes` 不涨 → **四个模式分钟之和 < 总运行分钟**，饼图/分布与「全屋墙钟约 N 分钟」对不上，且没有任何一处显示这段「未知工况」去哪了。这正是上一轮建议里「只在分母之外如实反映」的下半句，实现只做了分子那一半。
  - 建议：二选一。① 与 `StatusItemController` 已确立的「未识别就把原始码如实显示」口径对齐：加一个 `unknownMinutes` 字段单独累计并在 UI 明示；② 若不想加字段，就把未识别样本也排除出 `totalMinutes`（即把该样本视为「无有效工况证据」，不计入任何时间），这样分子分母同时收敛、比例保持自洽。倾向 ①——②会让「总运行时间」偏小，与电费/功率是同一批样本算出来的事实不符。

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:141-142`** — `.auto` 兜底在「室内/设定温度都取不到」时与原来的 `.cooling` **逐位等价**，README 宣称的「消除功率虚标」在该情形下不成立
  - 为什么是问题：把两个分支代入默认值算一遍即可证：
    - `case .cooling`：`delta = max(0, (indoorTemp ?? 26.0) - (targetTemp ?? 25.0)) = 1.0` → `power = 380 + 1.0*95 + windOffset`
    - `case .auto`：`indoor = 25.0, target = 24.0` → `indoor >= target` → `delta = 1.0` → `power = 380 + 1.0*95 + windOffset`
    
    两者**完全相同**（`windOffset` 同源）。而「模式码识别不出来」与「温度字段缺失」高度相关（设备上报不全时两者常同时发生），所以最需要兜底的那个场景恰好是这次改动不生效的场景。更要注意方向：`.auto` 在 `indoor < target` 时走制热曲线（上限 1650W > 制冷的 1450W），**并不保证比 `.cooling` 更保守**，只是更「按温差合理」。README 却写「瞬时功率估算未识别模式兜底由制冷切换为 `.auto`（基于中性温差计算，消除功率虚标）」——「消除虚标」这个断言没有依据。另：原 `var power: Double = 400.0` 初值现在成了纯摆设（所有分支都显式赋值或 return）。
  - 建议：要么把兜底改成真正的中性值（例如未识别时直接返回一个与模式无关的基准，或返回 `nil` 让上层跳过该设备的瞬时功率贡献），要么把 README 的措辞降级为「未识别模式改用 `.auto` 温差自适应曲线（不再固定按制冷记账）」，不要声称消除了虚标。若刻意保留 `.auto`，建议在 `case .auto` 上方注明「双 nil 时与 `.cooling` 等价，这是刻意的中性默认」——否则后来者会以为这里已经处理了缺失场景。

- **`Sources/HaierACApp/Views/MenuBarControlsView.swift:48-60`** — 新增的离线横幅只判 `device.online`，不判 `model.gatewayConnected`，与同文件的三态状态点、`DeviceControlView` 以及 README 的宣称都不一致
  - 为什么是问题：同一文件里紧邻的 `:178-193` 状态点与文案是**三态**（`!model.gatewayConnected` → `Theme.warning` / "重连中..."；`!isOnline` → `Theme.offline` / "设备离线"；否则运行/关机），`DeviceControlView.swift:73-84` 也是同样三态。但横幅 `if !device.online` 只看设备维度，且 `quickActionsPod(...).disabled(!device.online)` 同样只看设备维度。于是**网关断开、但设备上次上报为在线**时：横幅不出现、快捷操作仍可点，用户点下去只会吃到 `sendAttribute` 的「连接中断，指令未发送（自动重连中）」提示。而 README.md 这一条写的是「菜单栏与控制面板三态（运行/关机/离线）视觉无缝对齐」——实际只有两态对齐。上一轮 P2-4 修的是**颜色 token**，这里漏的是**状态维度**。
  - 建议：把横幅与 `.disabled` 的条件都改成 `!(device.online && model.gatewayConnected)`，文案分两句（网关重连中 / 设备未连网），与状态点保持同一套判据。可顺手抽一个 `controlAvailability(for:)` 之类的单一判据函数，避免第三处再各写一遍。

- **`Sources/HaierACApp/AppModel.swift:2482-2492`** — `sendAttributeToDevices` 静默过滤离线设备，且空选时的文案是错的
  - 为什么是问题：新增的 `let targetIds = deviceIds.filter { ... online ?? true }` 会**静默丢掉**离线设备，随后只播报 `已发送：\(desc) → \(sent) 台设备`（`sent` 是过滤后的数量）。用户勾了 3 台、其中 1 台离线，看到的是「已发送 → 2 台设备」，**不知道少的那台为什么少**。对比单设备的 `sendAttribute`（:2446-2450）会明确播报「⚠️ 设备离线：X 未连网，无法执行控制」——同一次提交里两条路径的披露口径不一致。另外 `guard !targetIds.isEmpty else { operationNotice = "⚠️ 选中的设备均处于离线状态" }`：当调用方传入的 `deviceIds` 本身就是空数组时（没有任何选中），也会报「均处于离线状态」，把「没选」说成「都离线」，属于把未发生的事讲成确定结论。
  - 建议：分开两种空结果——`deviceIds.isEmpty` → 「请先选择设备」；过滤后为空 → 「选中的 N 台设备均处于离线状态」。非空时在 `operationNotice` 里补上被跳过的台数（如「已发送 → 2 台设备（1 台离线已跳过）」），与 `sendAttribute` 的披露程度对齐。

- **`Sources/HaierACApp/AppModel.swift:2193-2200`** — 快速自愈路径的 1.5s 兜底 `Task` 没有代际校验，连续重试会让先发的任务把 `phase` 提前置回 `.ready`
  - 为什么是问题：新增的兜底是 `Task { await refreshTokenIfNeeded(); handle.reconnectImmediately(force: true); try? await Task.sleep(1.5s); if case .connecting = self.phase, !self.devices.isEmpty { self.phase = .ready } }`。这个 Task 不持有任何「第几次重试」的标识，也不取消前一次。用户连点两次「重试」（上一轮 P2-2 指出快速路径无反馈正是诱因，现在有了 `phase = .connecting` 但点击后 1.5s 内界面仍只有转圈）：任务 A 在 t=1.5s 醒来把 `phase` 置为 `.ready`，而任务 B 才刚开始握手——界面在网关尚未连通时就先「恢复就绪」了。后果是显示层提前乐观（`gatewayConnected` 仍为 false，所以状态点会照实显示「重连中」，**不是谎报**），属体验瑕疵而非数据问题。
  - 建议：给快速路径加一个 `reconnectGeneration` 计数器（进入时自增并捕获局部值，醒来后比对不等则直接返回），或干脆把兜底判定从「定时」改成「事件」——`onConnected` 已经会置 `.ready`，失败时保留 `.connecting` 并让错误态由 `onDisconnected` 驱动，就不需要这个定时器了。

- **`Sources/HaierACCore/Models.swift:79`** — `public var localizedName: String { desc }` 全仓无调用点
  - 为什么是问题：本轮新增，但 `grep -rn "localizedName" Sources/` 只命中定义这一行。它与既有的 `desc` 完全等价，是纯别名。本项目刚把模式码表收敛到 `ACModeCode` 一处，再加一个同义公开属性会让「该用哪个」重新变得不确定。
  - 建议：若暂无使用计划就删掉；若是为了给上层（如未来的本地化层）留接口，请补一行注释说明用途，否则会被当成死代码清掉。
