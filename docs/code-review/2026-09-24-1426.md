### P1 — 重要

- **`Sources/HaierACCore/VoiceCommandParser.swift:352-358`（`containsNegativeAction`）** — 否定意图检测是一张"否定词紧邻动作词"的子串表 `["别关","不要关","不用关","先别关","先不要关","暂不关","不能关","不可以关","别停","不要停","不用停","别开","不要开","不用开","先别开","先不要开","暂不开","不能开","不可以开","别启动","不要启动"]`，**在否定词与动作词之间插入任何字即失效**；而 `isAllPowerOff` 的关键词表里有 `"都关了"`、`"全关了"`、`"全都关了"`（`:352` 附近）。

  - **可复现输入**：`"全屋空调别都关了"` → `containsNegativeAction` 为 `false`（"别都关了"不含表中任一项）→ `isAllPowerOff` 命中 `"都关了"` → 解析成 `.turnOffAll` → **全屋关机**。同类：`"不要全部关掉"`、`"先别急着关"`、`"别马上关"`。
  - 为什么是问题：v1.9.34 的标题与 `README.md` 首条把这条列为"闭环 CR P2-3"，宣称能"避免家庭闲聊及口语否定句被误识别为电源动作"；实测只覆盖 20 个字面组合，且新加的 `testNegationProtection`（`VoiceCommandParserTests.swift:590-604`）里 10 条用例**全是紧邻写法**，守不住这条宣称。后果是"用户明确说不关，结果全屋关机"——与同版本刚修的冷暖倒置同级，且方向相反（一个是模式错、一个是电源错）。
  - 建议：改成结构判定而不是相邻子串——先定位否定词（`别` / `不要` / `不用` / `不必` / `无需` / `先别` / `暂不` / `千万` / `不能`），再看其后 N 个字符内是否出现动作词（`关` / `开` / `启动` / `停`）；或至少把常见插入词（`都` / `全` / `全部` / `一起` / `马上` / `再` / `急着`）纳入。测试必须补一条插字用例，否则这条修复没有回归防线。

- **`Sources/HaierACApp/Voice/VoiceCapsuleWindowController.swift:479`（`.cancelSchedules`）与 `Sources/HaierACCore/VoiceCommandParser.swift:180-183`（`isCancelSchedule`）** — v1.9.34 把"目标设备无定时任务 → 兜底清空全屋"这条越权路径删掉了（方向正确），但**没有区分"全屋取消"与"定向取消"两种意图**：`isCancelSchedule` 的关键词是 `["取消定时","取消倒计时","关闭定时","清除定时","删除定时","取消预约","别定了"]`，`"取消所有定时任务"` 同样命中；而 `resolveTargetDevices`（`:136-171`）在这种不含设备名的文本上会回退到 `menuBarDeviceId ?? allUnifiedDevices.first`，**恰好一台**，于是走单设备分支，只删那一台的定时。

  - 为什么是问题：用户说"取消所有定时任务"，实际只取消了一台；且 `VoiceCommandParser.swift:81` 生成的 `displayText` **仍是 `"取消所有定时与倒计时"`**——UI 文案与执行范围不一致，是这条缺口最直接的证据。另外多设备场景下（"取消客厅和主卧的定时"）会走 `executeMultiDeviceCommand`，其 `switch`（`:555`）没有 `.cancelSchedules` 分支，落到 `default` 报"该操作暂不支持多设备批量执行"（这一条是 v1.9.33 起的既有行为，非本轮引入，但与本轮修的"全屋取消"缺口是同一个语义空洞）。
  - 建议：仿照 v1.9.35 的 `parseAllRelativeTemperature` 做法，在解析层用 `isAllDeviceScope` 把"全屋取消"拆成独立的 `.cancelSchedulesAll`（或给 `.cancelSchedules` 加 `deviceIds: [String]?`），并在执行层让 `nil` 真正清空全屋；同时把 `displayText` 与最终 `markSuccess` 的范围口径对齐（要么都说全屋、要么都点名设备）。`executeMultiDeviceCommand` 补上多设备取消分支。

### P2 — 建议

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:107/114/121/128`** — 新增的 4 个公开计算属性 `coolingRatio` / `heatingRatio` / `dehumRatio` / `fanRatio` **零调用点**：全仓 grep 只命中定义处；`EcoEnergySection.swift:233-253` 自己在视图里用 `Int(round(Double(...) / Double(totalDevMins) * 100))` 重算了一遍。
  - 为什么是问题：同一提交既删/改了一堆东西，又留下 4 个"只有定义、没有消费"的公开 API；且它们内部的 `min(1.0, ...)` 钳制与视图里的不钳制形成两套口径——现在没有差异，但将来谁先被改就会分叉。本项目此前已把"新增零调用点 API"当作问题记过一次（`reachability(for deviceId:)`）。
  - 建议：让 `EcoEnergySection` 改用这 4 个属性（顺带把 `min(1.0,...)` 的钳制统一），或直接删掉它们。

- **`Sources/HaierACApp/Voice/VoiceCapsuleWindowController.swift:570`** — `case .adjustTemperature(let delta), .adjustTemperatureAll(let delta):` 里的 `.adjustTemperatureAll` 分支**不可达**（死代码）。`executeCommand` 的第一个 `switch`（`:187`）在 `:274` 就 `case .adjustTemperatureAll` 处理并 `return`；第二个 `switch`（`:340`）在 `:535` 把它列进 `break` 组；而 `executeMultiDeviceCommand` 的唯一调用点在 `:315`，位于第一个 switch 之后。
  - 为什么是问题：作者显然**预期**它会带着已解析的 `targetDevices` 走到这里（否则不会写进这个 case 的 pattern 里），这条预期落空说明意图与实现有偏差；死分支还会让后来者以为"多设备相对调温"已经走通。
  - 建议：确认后删掉 `.adjustTemperatureAll` 这个 pattern，只留 `.adjustTemperature`；若确实想让多设备相对调温复用这里，则应把 `:274` 的处理改为按 `targetDevices` 分派（但按 `parseAllRelativeTemperature` 的 `isAllDeviceScope` 前置守卫，目前它只会被全屋措辞触发，所以删掉更合理）。

- **`Sources/HaierACApp/StatusItemController.swift:294-302`（新增的「🔼 全屋统一升温 1°C」/「🔽 全屋统一降温 1°C」）** — 门禁是 `isEnabled = model.gatewayConnected && !onDevices.isEmpty`，**缺了 16/30°C 边界判定**；而同一提交给单设备项加的门禁是 `isControllable && isPowerOn && curTemp < 30.0`（升）/ `curTemp > 16.0`（降）（`:374`、`:383`）。
  - 为什么是问题：所有运行中设备都已在 30°C 时，"全屋统一升温 1°C"仍可点，会向每台下发一次 `targetTemperature = 30.0` 的冗余写（`AppModel.adjustTemperature` 的 `min(30.0, max(16.0, ...))` 把它夹回原值），而 `operationNotice` 仍宣称"已将全屋 N 台运行中的空调统一升温 1°C"——文案与实际不符。v1.9.34 的标题自己写着"状态栏/批量控制对称"，这条不对称就在同一个菜单里。
  - 建议：给这两项补上 `onDevices.contains { (model.attribute("targetTemperature", deviceId: $0.id)?.doubleValue ?? 26.0) < 30.0 }` 之类的边界条件，与单设备项同口径；或让 `adjustTemperature` 在"全部已到边界"时返回 0 并给出中性提示。

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:74-82`（`totalDeviceMinutes` 的迁移回填）** — 老记录（v1.9.34 及更早写入的 60 天历史）没有该字段，回填公式是 `max(coolingMinutes + heatingMinutes + fanMinutes + dehumMinutes + unknownMinutes, totalMinutes)`。
  - 为什么是问题：老记录里的"模式分钟"是**墙钟口径**（某个模式只要有任一设备在跑就 +1 分钟），不是设备机时；多设备环境下这些数值本身偏高，回填后却按设备机时口径参与占比展示，新旧记录在同一条曲线/同一个分布图里**口径不同**，而 README 与字段注释只写了"各工况机时之和恒等于总机时"（这条对新写入成立，对回填不成立）。
  - 建议：在字段注释与 README 里补一句"v1.9.34 及更早记录的工况分钟为墙钟口径，其占比仅供参考"，或在 UI 上对早于该版本的日期标注；如果希望口径统一，需要一次显式的历史回填/作废策略。
  - 不确定项：我没有老版本写出的真实 `historyRecords` 样本，上述结论基于读写两侧代码的静态对照，**非实测数据**。
