### P1 — 重要

- **`Sources/HaierACApp/AppModel.swift:586-591`（`calculateFilterWearFactor` 的模式分支）** — 模式码表用错：送风被按除湿计，等效工时高估 53%；而仓库里已经有三套互不相同的模式码表。
  - 为什么是问题：`"2"` 在本项目里**就是送风**，不是除湿。
    - 既有口径（两处）：`EnergyAnalyticsEngine.swift:142-166`（`estimateInstantaneousPower`）与 `:233-237`（`accumulateSample`）都是 `"0"=制冷 / "1"=制热 / "2"=送风 / "3"=除湿`。
    - App 自己的写入路径：`AppModel.swift:1089` 送 `"0"` 并注释「制冷模式」；`AppModel.swift:1569` 送 `"2"` 并注释「送风」。
    - `VoiceCapsuleWindowController.swift:181-188` 的回退表是第三套：`制冷=0 / 除湿=1 / 送风=2 / 制热=4 / 自动=6`。
    - 新函数是第四套：`"0"=制冷 / "2"=除湿 / "4"=制热 / "6"=送风`。
    - 后果：设备回读 `operationMode == "2"`（送风）时套用 **1.30（除湿）** 而非 0.85（送风）→ 等效工时多算 53%，`FilterCareSheet` 的「预计还可使用约 N 天」被腰斩；`"1"`/`"3"`（制热/除湿）落进 `default 1.00`；`"4"`/`"6"` 在本项目里根本不是合法模式码，是死分支。README 承诺的「送风 0.85x / 除湿 1.30x」在数字分支下永远取不到。
  - 建议：把模式码收敛到**唯一一处**（如 `HaierACCore` 加 `enum ACModeCode: String { case cooling = "0", heating = "1", fan = "2", dehumidify = "3" }` + `init?(rawValue:)` / `init(desc:)`），`calculateFilterWearFactor`、`EnergyAnalyticsEngine`、`VoiceCapsuleWindowController` 全部改用它；统一之前，至少先把新函数的数字分支改成 0/1/2/3 并删掉 4/6。
  - **不确定**：本轮无法静态确证运行时 `attrs["operationMode"].stringValue` 一定返回数字码（云侧也可能回中文 desc；`Theme.modeCategory` 与 `AppModel:1571` 的风速匹配都是按中文 `desc` 匹配的，说明两条路径并存）。但「2 = 送风」是 App 自己写出去的值，所以只要设备回读数字码，这条就成立。**验证方式**：在 `accumulateMinuteTick`（AppModel.swift:844）里临时打一行 `AppLog.log("mode=\(mode) wind=\(windSpeed)")`，或直接看设备详情里 `operationMode.valueRange.dataList` 的 `data` 取值。

- **`Sources/HaierACApp/StatusItemController.swift:147-157`（`showPanel` 里重建 rootView）** — 每次打开 popover 都重建整棵视图树，`MenuBarControlsView` 的 `@State` 被重置，多设备选择失效并与状态栏标题显示不同设备。
  - 为什么是问题：`self.popover` 只在 159-171 创建一次、**全文件没有任何 `popover = nil`**，所以 `if let existing = self.popover` 分支每次都会命中，`host.rootView = AnyView(...)` 每次都会执行。SwiftUI 里重新赋 rootView 等于换掉视图身份 → `MenuBarControlsView.swift:12` 的 `selectedDeviceId`、`:14` 的 `selectedSleepCurveId` 每次打开都回到 `nil`。
    而 `currentDevice` 的兜底是 `activeDevices.first`（MenuBarControlsView.swift:29-32），**不看** `model.menuBarDeviceId`；状态栏标题走的是 `menuBarDeviceId ?? devices.first?.id`（AppModel.swift:414）。于是：用户在 popover 里切到第二台（`set` 同时写了 `selectedDeviceId` 与 `model.menuBarDeviceId`）→ 关闭 → 再打开 → popover 头部回到第一台，状态栏标题却还停在第二台，两处显示不同设备。
  - 建议：只在配色方案**真的变了**时才重建——记住上次应用的 `model.themeMode.colorScheme`，相同就跳过重建（这是最小改动，也保住了原意图）；或不用 `.preferredColorScheme`，改设 `host.view.appearance` / `popover.appearance`。另建议把 `currentDevice` 的兜底改成 `model.menuBarDeviceId ?? activeDevices.first?.id`，与状态栏标题对齐。

### P2 — 建议

- **`Sources/HaierACApp/AppModel.swift:612-640`（`checkFilterHealthAlert`）** — 7 天节流只存内存，重启即失效，导致「每次启动都推一次」；洁净度公式重复实现。
  - 为什么是问题：`lastFilterAlertDates`（:612）是普通 `private var`，App 一重启就空；只要洁净度 ≤20%，启动后第一次采样（约 1 分钟内）就会再推一条系统通知——用户清洗前每开一次 App 收一条。另外百分比算法与 `filterCleanlinessPercentage(for:)`（:516-521）是两份实现，`250 * 60` 这个常量在 `AppModel.swift` 里已出现 3 次（:517、:527、:615），`FilterCareSheet.swift:186` 还有第 4 次。
  - 建议：`lastFilterAlertDates` 按 `deviceFilterCleanedDates` 的做法落 UserDefaults；百分比直接调 `filterCleanlinessPercentage(for: deviceId)`；把 `250 * 60` 提成一个 `static let filterServiceLifeMinutes`。
  - 附带：`:637` 的 `try? await ...add(req)` 把失败吞了。若通知权限被拒（`requestNotificationPermission()` 只在首次添加定时任务时调用，见 :1802），README 承诺的「跌破 20% 自动推送」会静默失效——建议 `catch` 里写一条 `AppLog`。

- **`Sources/HaierACApp/Audio/AmbientSoundEngine.swift:111-113`（`play()` 新增的 `else` 分支）** — 音量是瞬跳，会有可听的爆音；根因是 `volume.didSet` 不触发过渡。
  - 为什么是问题：`volume.didSet`（:45-50）只更新 `targetVolume`，而实际增益是 `activeGain`。所以播放中拖动音量条**当场没有声音变化**（既有问题），要等下一次 `play()` 才生效；而这次新加的 `else { self.activeGain = self.targetVolume }` 让「当前增益 > 目标音量」（用户调小音量）变成**一个采样帧内直接跳变**，不是淡变——渲染回调逐帧读 `activeGain`，跳变会出爆音。原代码这里什么都不做，所以是「从无声到爆音」，不算严格回归，但新行为比旧行为更容易被听出来。
  - 建议：把过渡逻辑放进 `volume.didSet`（`activeGain → targetVolume` 起一段 0.3s 左右的淡变，同样带 `fadeGeneration` 熔断），`play()` 的 `else` 分支只保留兜底赋值。

- **`Sources/HaierACApp/Views/FilterCareSheet.swift:186`** — 「预计还可使用约 N 天」硬编码 6 小时/天，且没乘 `currentWearFactor`。
  - 为什么是问题：同一个弹窗上边展示的是「空气动力学等效工时（含风量与凝露加权）」，下边的剩余天数却用 `(15000 − 分钟) / (6*60)` 这个固定 6h/天反推，两者口径不一致（等效工时已经含负荷系数，天数又按裸墙钟折算，等于把加权算了一半）。6 小时这个数字也没有任何出处或说明。
  - 建议：改用项目已有的真实日均运行时长（`EnergyAnalyticsEngine` 的 `totalMinutes`，`EcoEnergySection` 已在展示「全屋墙钟约 N 分钟」）反推；退一步至少把文案写成「按每天 6 小时估算」，并把 6 提成常量。
