### P1 — 重要

- **`Sources/HaierACApp/StatusItemController.swift:263` / `:285` / `:296` / `:307` / `:331`（5 处 `isEnabled` 赋值）** — 这些门禁**按 Apple 官方文档是死代码**：`NSMenuItem.isEnabled` 在 `autoenablesItems` 为 `true` 时不生效，而本项目的菜单从未关闭该开关，也没实现 `validateMenuItem:`
  - 为什么是问题：`NSMenuItem.isEnabled` 的文档原文是 —— *"This property has no effect unless the menu in which the item will be added or is already a part of has been sent `setAutoenablesItems:NO`."*（Apple Developer Documentation, AppKit / NSMenuItem / isEnabled）。而 `NSMenu.autoenablesItems` **默认为 true**，`NSMenu.update()` 会 *"Enable or disable the menu items of the menu based on the NSMenuValidation informal protocol"*。全仓 `grep -rn 'autoenablesItems\|validateMenuItem' Sources/` → **0 命中**，即开关从未关闭、`NSMenuValidation` 也从未实现。菜单的挂载方式是 `StatusItemController.swift:384-386`（`statusItem?.menu = menu` → `performClick(nil)` → 置 nil），展示时 AppKit 会跑一遍 `update()`；由于 `self` 实现了 `toggleDevicePower(_:)` / `setQuickCooling(_:)` / `setQuickHeating(_:)` / `turnOffAllDevices` / `togglePrimaryPower`，这 5 个条目会被**自动重新启用**，手工设的 `isEnabled = false` 被覆盖。
  - 影响面（已核实，故不按"错误下发"定级）：离线设备并不会真的收到指令——`AppModel.sendAttribute`（`AppModel.swift:2557-2560`）与 `sendAttributeToDevices`（`:2602-2610`）各自都有内部守卫。所以真实后果是：**对不可达设备，菜单项仍显示为可点击，点击后靠一句错误提示兜底**，而 README 本轮宣称的「Fail-Closed 熔断」在这一层没有生效。**`isEnabled` 是这套菜单唯一的可达性视觉信号，它失效等于这个信号不存在。**
  - 建议：在 `showContextMenu()` 里 `let menu = NSMenu()` 之后补一行 `menu.autoenablesItems = false`（`devicesMenu` / `devSubmenu` 同理，或对每个子菜单都设）。本项目所有菜单项都已显式设 `target`，且没有依赖自动启用语义的条目，关掉它是安全的、且能让现有 5 处 `isEnabled` 立刻生效。
  - **验证方式**：把设备置为离线，右键状态栏图标——若「空调设备控制矩阵…」里的「关机 / 一键制冷 26°C / 一键制热 20°C」仍可点击，本条即成立。

### P2 — 建议

- **`Sources/HaierACApp/Views/MenuBarControlsView.swift:96-98`（配合 `:755-756` 的「停止」按钮）** — 门禁加在了整个睡眠卡片上，把**纯本地的「停止」动作一起锁死**了；设备离线时用户反而失去了退出手段
  - 为什么是问题：`stopSleepCurve()`（`AppModel.swift:1331-1345`）**不向设备发送任何指令** —— 它只做 `archiveSleepSession`、清 `activeSleepSession`、停本地白噪音、`wakeScheduler()`、`writeWidgetSnapshot()`。而 `sleepControlPod` 的「运行中」分支里那个「停止」按钮（`:755-756`）现在被 `.disabled(!reachability.isControllable)` 覆盖。于是出现一个反直觉的状态：设备在睡眠过程中掉线 → 卡片变灰、进度照常走 → 用户点不了「停止」，只能去主窗口的睡眠区（`SleepCurveSection.swift`）才能退出。本轮加门禁的目的是"阻断会真下发指令的幽灵点击"，`startSleepCurve` 已被入口守卫覆盖，**「停止」属于被误伤**。
  - 建议：把 `.disabled` 从整个 pod 下移到「开启睡眠」分支（或按 `model.activeSleepSession != nil` 区分：运行时只禁用与设备交互的部分、保留「停止」）。**同类复核**：`FilterCareSheet.swift:332-334` 的「中止自清洁」也被门禁覆盖，但那条**是对的**——`stopSelfCleaning()`（`AppModel.swift:807-822`）确实会向设备下发 4 个 `*Status = false`，属设备侧动作，保持禁用无误。

- **`Sources/HaierACApp/StatusItemController.swift:263`（`turnOffAllItem` 的标题计数）** — 「关闭全屋空调 (N 台运行中)」的 N 来自**包含离线设备**的 `onDevices`，与点击后实际会下发的目标集不一致
  - 为什么是问题：`onDevices`（`:255-258`）的判据是 `model.attribute("onOffStatus", deviceId:)?.boolValue == true`，只读本地属性缓存、**不看 `online`**；而 `turnOffAllDevices()`（`:418-421`）最终走 `sendAttributeToDevices`，其内部会按 `online` 过滤（`AppModel.swift:2602-2604`）。若一台设备属性里仍记着"开机"但已离线（掉线前最后一次上报的陈旧值），标题会把它计入「运行中」，实际却跳过它。用户看到「(3 台运行中)」，实际只关了 2 台，且不会有针对第 3 台的明确提示（`sendAttributeToDevices` 的 `offlineCount` 分支在 `targetIds` 非空时只是静默过滤）。
  - 建议：把 `onDevices` 的判据补上可达性 —— `model.reachability(for: dev).isControllable && attribute(...)?.boolValue == true`，让标题与实际目标集同源；或把标题改成「关闭全屋空调」不带计数，避免口径不一致。

- **`Sources/HaierACApp/AppModel.swift:688-695`（`calculateFilterWearFactor` 的 `selfCleaningBonus`）** — 「蒸发器自清洁 → 滤网负荷减免」的因果链与物理量对不上，且这个 0.90 会**永久改变**已累积等效工时的口径
  - 为什么是问题：这条改动的语义是"蒸发器（室内机翅片）完成 56°C 自清洁后，**滤网**积尘截留速率减缓 10%"。滤网在蒸发器**上游**、承担的是截留浮尘，蒸发器自清洁除的是翅片上的污垢与霉菌，两者不是同一条链路，`0.90` 没有可对应的物理量（对比同函数里另三个因子——风量通量、冷凝结露、环境湿度——都能落到具体机制上）。更重要的是它**改变了既有数据的可比性**：`filterAccumulatedMinutes` 是累加量，`wearFactor` 只是每一步的乘数，于是同一台设备在"有保护期"与"无保护期"两段时间里产生的等效工时**不同尺度**，滤网洁净度百分比（`filterCleanlinessPercentage`）与"建议保养周期"的对应关系被悄悄改写；而 `max(0.4, ...)` 的下限也为此从 0.5 放宽到 0.4（`:695`），等于承认乘数可以更低。
  - 建议：若这个联动是**产品有意为之**，请在 `README` 与函数注释里把它写成"产品策略"而非"物理模型"（现在注释用的是"翅片无污垢杂菌、风道通畅阻力小"这类物理因果措辞），并在滤网卡片上标明"含自清洁减免"以免用户对不上保养周期。若只是想让自清洁有正向反馈，更干净的做法是**不改动累加量**、只在展示层给一个提示（例如洁净度不因保护期变化，但显示"翅片健康"徽章）——避免历史数据的口径漂移。
  - 注：`selfCleaningBonus` 的**实现本身没错**（`deviceId` 为 `nil` 时取 1.00，`isSelfCleaningProtectionActive` 只看 `7 * 86400` 秒差，`deviceSelfCleaningDates` 的持久化与回读成对），本条只针对因果口径。
