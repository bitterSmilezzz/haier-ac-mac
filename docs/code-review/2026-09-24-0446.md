### P1 — 重要

- **`Sources/HaierACCore/HaierGatewayClient.swift:68-79`**（配合 `:265-273` 的 `reconnectImmediately`）— `connect()` 没有「已有连接在途」的防护，新快速自愈路径会制造不被取消的孤儿 WebSocket 连接
  - 为什么是问题：`connect()` 的全部守卫只有 `guard let session, let gatewayURL, !stopped`，随后 `let task = session.webSocketTask(with: url); self.task = task; task.resume()` ——**直接覆盖 `self.task`，不取消上一个**。`reconnectImmediately()` 的守卫是 `guard !isConnected`，而 `isConnected` 只在 `didOpen` 里才置 true，**握手期间它是 false**，所以快速路径可以在一个连接正在握手中时再次进来，把旧 task 顶掉。旧路径不存在这个问题：`handleDisconnect`（`:245-247`）先做了 `self.task?.cancel(); self.task = nil` 再调度重连，所以退避路径是安全的——**这个缺口是 v1.9.24 新开的快速路径独有的**。
    后果有两层：① 被顶掉的 task 已经 `resume()` 且从未 `cancel()`，它的 `didOpen`/`didClose` 回调都会被 `webSocketTask === self.task` 的代际校验挡掉（`:83`、`:93`），于是**没有任何路径会去关它**——socket 一直挂着，服务器侧多出一条会话。② 该 task 在 `connect()` 里同时启动了 `receiveLoop(task)`（`:78`），而 `receiveLoop` 的循环条件是 `self.isConnected`（`:154`）：如果新连接先于孤儿循环的首次判断完成握手，`isConnected` 为 true，**孤儿循环不会 break，会继续 `receive()` 并处理消息** → 属性推送被重复应用、订阅响应被重复处理。
    可达性：需要在握手窗口（几十毫秒到数秒，网络差时更长）内被触发第二次。触发源有三处——用户反复点错误页「重试」、`NetworkPresenceGuard` 的两个自愈点（网络恢复、切回家庭 Wi-Fi）、以及 `AppModel.swift:2168` 那个周期性后台重试循环。**而网络恢复恰恰就是网络不稳定的时刻**，所以不是理论场景。P2-2 会进一步放大它（快速路径不给任何视觉反馈，用户会连点）。
  - 建议：在 `connect()` 开头补上在途防护，`self.task != nil` 恰好等价于「有一次连接在途或已连接」（`handleDisconnect` 与 `stop()` 都会把它置 nil），所以 `guard self.task == nil else { return }` 即可；或者按 `handleDisconnect` 的形状，在 `reconnectImmediately()` 里 `task?.cancel(); task = nil` 之后再 `connect()`。前者更安全（快速路径若发现已在连就自然 no-op，不会产生第二条连接）。

### P2 — 建议

- **`Sources/HaierACApp/Energy/EnergyAnalyticsEngine.swift:141` 与 `:246`** — 两处 `ACModeCode.match(from:, default: .cooling)` 与项目刚确立的「未识别 → 中性」口径不一致
  - 为什么是问题：就在同一个提交里，`AppModel.calculateFilterWearFactor` 把「未识别模式」明确定义为回归**中性**基准（`README.md` 的措辞是「彻底消除虚标高估」）；但能耗引擎把未识别模式**显式**映射成 `.cooling`。查同文件功率表：`fan` 上限 65W、`dehumidify` 300–600W、`cooling` 180–1450W、`heating` 220–1650W —— 制冷是第二高的一档。于是设备上报一个本枚举不认识的模式码（如 `"5"`，或本地化字符串未命中关键字）时，能耗估算按制冷曲线记账，**功率偏高**；`:246` 处更直接：`sampleMode` 用于累计 `runningCooling` 等运行占比，未识别样本会被计成「制冷运行」，**扭曲运行模式分布**。注意这不是本轮引入的行为变化（改前 `match` 的兜底也是 `.cooling`），只是本轮把默认值写成了显式参数、因而更容易被当成有意决策——而它与同提交里的口径是相反的。
  - 建议：`:141` 改用 `default: .auto`（该分支本身就是按室内/设定温差智能判别制冷或制热，是真正的中性档）；`:246` 建议改为**不计入任何模式**——保留 `match(from:)` 的 `nil`，未识别样本既不加 `runningCooling` 也不加其他计数，只在分母之外如实反映。若确实想保守高估，请在注释里写明理由（现在没有注释解释为什么这里选制冷）。

- **`Sources/HaierACApp/AppModel.swift:2186-2199`** — `retryConnection()` 的快速自愈路径不设置 `phase`，用户点「重试」看不到任何反馈
  - 为什么是问题：旧实现无条件 `phase = .connecting` 再走 `refreshTokenIfNeeded() + connectAndLoad()`。现在只要 `gatewayHandle != nil && !gatewayConnected` 就 `handle.reconnectImmediately(); return`，**`phase` 保持原值**（错误页场景下即 `.error`）。成功路径没问题——`onConnected` 回调会把 `phase = .ready`（`AppModel.swift:2354-2357`）；但**失败或挂起时界面毫无变化**，用户会以为按钮没生效而反复点击，而每次点击都会走进 P1 那条会顶掉在途连接的路径。另外这条路径也跳过了 `refreshTokenIfNeeded()`（`:2168` 的后台自愈路径是刷新过的），token 恰好在过期边界时会直接连失败。
  - 建议：进入快速路径前先 `phase = .connecting`（成功时由 `onConnected` 覆盖为 `.ready`，失败时维持 `.error` 的语义需要保留原值 —— 可考虑加一个独立的「正在重连」子状态或复用现有的连接中指示），至少让「重试中」有可见反馈；并考虑在快速路径上也串一次 `refreshTokenIfNeeded()`，与后台路径保持一致。

- **`Sources/HaierACApp/Audio/AmbientSoundEngine.swift:38-63`** 与 **`README.md` / `README.en.md`（v1.9.24 条目）** — 实现用的是 `os_unfair_lock`，文档却宣称「无锁」
  - 为什么是问题：这次改动本身是**对的、有价值的**——旧写法在 `AVAudioSourceNode` 渲染回调里通过 `[weak self]` 闭包读 `@MainActor` 类的 `currentType`/`activeGain`，是确凿的数据竞争（TSAN 会报）；改成 `AudioRenderParameters` 快照 + 显式锁，并借 `init` 里补一次 `setGain/setType` 来补偿「属性观察器在初始化期不触发」——这两点都考虑到了。但文档把方案描述成「**无锁**自愈引擎 / **Lockless** CoreAudio Realtime Engine / 实时音频渲染回调**无锁**竞争读取」，而 `os_unfair_lock` 是一个互斥锁（`os_unfair_lock_lock` 会阻塞并做优先级捐赠）。**文档与实现不符**，而这个项目的 README 是要给别的 Agent 当契约读的。附带一提实时性权衡：渲染回调里取锁并非 Apple 对 realtime audio 的推荐做法（主线程若在 `setGain` 的临界区内被抢占，音频线程会被阻塞到抢占结束，理论上可能造成丢帧/爆音）——不过临界区只有两次字段读、纳秒级，实践风险很低，作为权衡可接受。
  - 建议：二选一。① 改文档：把「无锁」改为「`os_unfair_lock` 纳秒级轻量互斥 + 原子快照」，如实描述；② 若确实要「无锁」，渲染线程侧应换成真正的无锁双缓冲（原子指针交换 `ManagedAtomic`/`OSAllocatedUnfairLock` 之外的方案），把「无锁」变成事实。
